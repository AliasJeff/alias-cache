# 测试与验证标准

## 1. 测试分层

### 单元测试

覆盖解析器、响应编码、可控时钟、TTL 计算、数据结构、日志条目、锁范围和状态转换。

### 协议测试

使用真实 TCP 连接验证半包、粘包、Pipeline、RESP2/RESP3 和错误响应。

### 状态机测试

验证：

- 同一日志在多个状态机副本上产生相同结果。
- 日志序列化后重放结果不变。
- 事务和多 key 操作具有预期原子性。
- 快照恢复后继续执行日志结果一致。
- 随机操作序列在多个状态机实例上保持一致。
- 多 key 操作在快照增量恢复后仍然原子。

### 集群测试

至少包含三节点：

- 初始选举
- 写入复制
- Leader 转换
- Follower 加入
- Follower 追赶
- 成员移除
- ReadIndex 线性一致读
- 少数派分区不可提交
- Leader 响应丢失后的请求状态

### 故障注入

逐步加入：

- 杀掉 Leader
- 杀掉 Follower
- 延迟或丢弃 RPC
- 网络分区
- 日志文件截断
- 快照传输中断
- 进程在 fsync 前后退出
- 磁盘空间不足
- fsync 返回错误
- 节点在日志追加、提交、apply 和快照发布的不同阶段退出
- 旧快照与新快照同时存在

故障测试必须使用测试控制面等待明确状态，不使用固定时间睡眠猜测选举或恢复完成。

## 2. 一致性检查

测试不能只检查“请求成功”。还要检查：

- 未提交写入不会出现在新 Leader。
- 已提交写入在重启后存在。
- 两个节点不会同时安全接受冲突写入。
- 快照和日志重放不会产生重复或丢失操作。
- TTL 在不同副本和恢复后保持一致。
- Leader 失去多数派时没有成功写入。
- 快照安装失败时旧状态仍可恢复。
- 日志截断后旧 Leader 尾部不会复活。

## 3. 性能测试

每次 benchmark 必须记录：

- CPU、内存和磁盘类型
- 节点数量
- 客户端数量
- key/value 大小
- 读写比例
- 是否启用 TLS
- 是否启用 fsync
- 延迟百分位数
- 是否使用线性一致读
- 快照和日志配置
- 错误率、恢复时间和内存峰值

只报告可重复的结果，不用单一峰值代表系统能力。

## 4. 发布门禁

合并前至少通过：

```text
cargo fmt --check
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

集群或故障相关功能还必须通过对应的多节点测试。

## 5. 完成证据

每个计划阶段完成时，提交说明中必须列出：

- 运行过的命令；
- 测试数量和关键场景；
- 失败注入点；
- 性能或资源结果；
- 未覆盖的风险；
- 是否修改了协议、日志或快照格式。
