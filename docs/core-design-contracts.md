# 核心设计契约

本文档冻结 alias-cache 在实现早期必须保持稳定的核心语义。后续代码可以优化实现，但不能在没有更新本文档和对应测试的情况下改变这些契约。

## 1. 术语与范围

- **状态机**：只处理已经提交的 Raft 操作，不直接接收 TCP 请求。
- **外部请求**：来自 Redis 客户端的请求，可能是读、写、事务或连接级操作。
- **复制操作**：可以序列化、进入 Raft 日志、在每个副本上按相同顺序重放的操作。
- **应用位置**：状态机已经应用的最大日志位置。
- **提交位置**：Raft 已确认可以应用的最大日志位置。
- **逻辑时间**：参与状态机结果计算的、随复制日志传播的时间值。

第一版只支持单 Raft group、固定数据库数量和 Leader 提供一致性读写。Redis Cluster 分片不是第一版目标。

## 2. 状态机操作模型

状态机操作必须满足：

1. 所有字段都可序列化。
2. 相同初始状态和相同操作序列得到相同状态和响应。
3. 操作不能读取本地墙上时钟、随机数、线程调度结果或节点 ID 来决定业务结果。
4. 操作的响应也必须可以在 Leader 和 Follower 上得到相同结果。
5. 不支持的操作必须在进入 Raft 前被拒绝，不能把“近似实现”写入日志。

建议将日志请求分成以下几类：

- `ReadBarrier`：不修改状态，但要求 Leader 建立读屏障。
- `SingleKeyWrite`：单 Key 写入或读改写。
- `MultiKeyRead`：一次性读取多个 Key。
- `MultiKeyWrite`：一次性修改多个 Key。
- `Transaction`：包含有序子操作的单个复制单元。
- `Membership`：由 Raft 成员管理，不进入业务状态机。

连接状态、认证状态、订阅状态和事务队列不属于复制状态机；数据库内容、TTL、逻辑时间和事务执行结果属于复制状态机。

## 3. 锁和原子性模型

第一版采用保守的状态机并发模型：

- 单 Key 读允许并发。
- 单 Key 写必须串行进入状态机。
- 多 Key 读和多 Key 写必须获得统一的状态机访问范围。
- 同一命令不能在读取依赖 Key 后释放访问范围，再异步修改目标 Key。
- 多 Key 访问顺序必须稳定，避免按客户端参数顺序获取多个锁造成死锁。

快照期间，每个可变值需要有版本或等价的 CAS 条件。对于跨多个 Key 的操作，快照增量必须保存完整操作及其全部依赖版本，不能把一个原子操作拆成多个可以被中间观察的外部操作。

## 4. Raft、日志和响应语义

写请求的成功响应必须满足：

1. 请求已经通过参数和权限校验。
2. 日志已经持久化到本节点定义的安全边界。
3. Raft 已经提交该日志。
4. Leader 状态机已经应用该日志并生成响应。

Follower 的外部写请求不得直接修改本地状态。第一版可以选择返回包含 Leader 地址的稳定错误，或由服务端转发到 Leader；两种方式不能在同一配置下产生不明确的混合行为。

Raft 存储至少需要持久化：

- 日志条目；
- 当前 vote；
- last purged log；
- membership 元数据；
- 快照元数据；
- 能够判断状态机应用位置的元数据。

日志追加、截断、压缩和快照安装必须定义崩溃后的可恢复顺序。任何恢复错误都必须阻止服务以空状态启动。

## 5. 线性一致读

第一版默认只提供 Leader 线性一致读：

1. 请求到达当前 Leader。
2. Leader 通过 ReadIndex 或等价的多数派确认建立读屏障。
3. 等待本地状态机应用到屏障位置。
4. 读取状态机并返回结果。

Follower 读不作为默认能力。后续若实现 lease read，必须单独说明时钟漂移、租约失效、网络分区和 Leader 变更行为。

## 6. TTL 和逻辑时间

TTL 的复制结果使用日志携带的逻辑时间和绝对过期时间，不使用副本本地墙上时钟决定业务结果。

建议采用以下模型：

- 每个写入日志携带 `write_time`。
- `write_time = max(current_write_time, current_read_time, local_physical_time)`。
- 应用日志前先推进状态机写逻辑时钟。
- `EX/PX` 计算出的过期点是逻辑时间域中的绝对值。
- 读请求可以生成单调不减的读逻辑时间，用于判断可见性，但不直接修改复制状态。
- 物理过期线程只负责尽快清理已经确定过期的值，不改变业务判断。
- 空闲期间可以由 Leader 周期性提交轻量时间推进或清理操作；是否启用必须由配置控制。

必须在实现前冻结：

- 过期条件使用 `now >= expire_at`；
- `TTL/PTTL` 对剩余时间的舍入；
- 不存在 Key、无 TTL Key 和已过期 Key 的返回值；
- `SET` 覆盖、`KEEPTTL`、`PERSIST` 和修改值命令的 TTL 继承规则；
- 逻辑时间溢出和非法负数的错误行为。

## 7. 快照协议

快照采用类似 cache-cat 的三阶段协议：

- `Start`：遍历当前状态；同时应用的写操作更新内存并进入增量队列。
- `Tail`：在同一把元数据锁下切换状态、排空增量队列，并确定快照的 last applied log id。
- `End`：增量数据写入完成、文件 fsync、原子发布完成后结束。

每个快照必须包含：

- magic、格式版本和校验信息；
- 数据库数量；
- 状态机最后应用日志位置；
- membership 元数据；
- 逻辑时钟；
- 所有值及其过期时间；
- Start 阶段产生的有序增量队列；
- 能够识别快照所属集群或节点格式的元数据。

快照安装流程：

1. 写入唯一临时文件。
2. 校验长度、版本、校验和和元数据。
3. 暂停物理过期 worker。
4. 在明确的状态切换或锁保护下替换状态机。
5. 先恢复完整数据，再按 CAS/版本顺序恢复增量。
6. 恢复逻辑时钟和过期调度。
7. fsync 后原子发布当前快照。
8. 清理旧日志和临时文件。

任一步失败都必须保留旧快照和旧状态，不能发布半成品。

## 8. 资源和失败边界

所有外部输入都必须受限：

- 单帧大小；
- 数组元素数；
- 嵌套深度；
- Key 和 Value 大小；
- Pipeline 长度；
- 单连接并发请求；
- 事务长度；
- 快照大小；
- 日志大小；
- 集群节点数。

进程崩溃、网络延迟、消息丢失、磁盘满、fsync 失败、日志尾部损坏、快照传输中断和 Leader 响应丢失都属于需要定义行为的失败。

## 9. 格式版本和升级

日志、快照和状态机操作都必须包含可识别的格式版本。

- 新版本读取旧格式时，要么提供明确迁移，要么在启动/安装阶段拒绝。
- 未知版本、错误 magic、长度溢出和校验失败必须是硬错误。
- 不能通过“忽略未知字段”掩盖语义不兼容。
- 日志格式、快照格式和协议兼容性分别版本化。
- 发布前必须验证旧数据目录在目标版本下的行为。
- 降级是否支持必须明确记录；第一版默认不承诺自动降级。

## 10. 请求提交和幂等性

客户端在提交成功但响应丢失时无法判断请求状态。第一版必须：

- 对不可确认的写请求返回明确的客户端状态；
- 不自动重试非幂等操作；
- 为每个请求预留可选 request id；
- 对 `SET`、`DEL` 和 `MSET` 等幂等操作与 `INCR` 等非幂等操作分别测试；
- 后续如果加入去重，去重状态必须进入持久化/快照语义，不能只放在连接内存中。
