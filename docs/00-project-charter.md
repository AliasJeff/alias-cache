# 项目章程

## 1. 我们要做什么

alias-cache 是一个使用 Rust 编写的 Redis 协议兼容分布式内存 KV 存储。

它通过 Raft 复制写操作，让多个节点对同一份状态机日志达成一致；通过 WAL 和快照在节点重启后恢复状态；通过 RESP2/RESP3 让现有 Redis 客户端可以连接和使用。

项目的核心问题是：

> 在保持内存读取效率的同时，如何让已提交的写入具备可解释、可测试的高可用和一致性语义。

## 2. 设计取舍

### 2.1 内存状态机

业务数据主要存放在内存状态机中，读取不依赖磁盘。持久化通过 Raft 日志和快照完成。

这意味着：

- 读延迟低。
- 写入需要经过共识和日志持久化。
- 内存容量是明确的运行约束。
- 快照和重放是可靠性的核心组成部分。

### 2.2 强一致优先

默认只允许 Leader 接受写入。读请求根据明确的读策略执行，早期优先实现线性一致读，之后再评估租约读。

项目不把“最终会同步到副本”称作强一致，也不把客户端缓存一致性和存储内部一致性混为一谈。

### 2.3 Redis 兼容是边界，不是全部目标

我们实现 Redis 的协议和一组经过验证的命令语义，但不承诺一次性兼容完整 Redis。

每个支持的命令都必须明确：

- 参数和错误行为
- RESP2/RESP3 返回形式
- 是否进入 Raft 日志
- 是否允许在事务中执行
- 是否会依赖本地时间
- 快照和重放如何保持一致

## 3. 最终功能范围

### 核心存储

- String、Hash、List、Set、Sorted Set
- TTL、过期删除和持久化
- 多数据库或明确的单数据库限制
- Pipeline、事务和批量操作

### 分布式能力

- Raft Leader 选举
- Follower 日志复制
- Leader 转发
- 线性一致读
- Learner、成员加入和安全移除
- WAL、日志截断和日志清理
- 全量快照、快照安装、恢复和落后节点追赶
- 节点重启和崩溃恢复

### 协议与接入

- RESP2
- RESP3
- AUTH、HELLO 和基础连接命令；`CLIENT` 不在当前稳定兼容范围
- Pipeline
- 基础 Sentinel 风格主节点发现

### 工程能力

- TLS
- 运行状态和指标
- 日志、诊断和健康检查
- 基准测试
- 故障注入测试
- Docker 和本地三节点运行脚本

详细的命令支持范围、版本基线、客户端路由和故障语义见：

- [兼容性与故障模型](compatibility-and-failure-model.md)
- [核心设计契约](core-design-contracts.md)

## 4. 明确暂缓的内容

- Lua 脚本
- Pub/Sub 和阻塞命令
- Stream
- Bitmap、HyperLogLog、Bloom Filter
- Redis Cluster 分片
- 复杂内存淘汰策略
- 管理 UI

这些功能不是永久禁止，而是必须等核心日志、快照和恢复链路稳定后再加入。

## 5. 参考实现边界

项目参考本地 `cache-cat` 开源仓库的以下设计：

- OpenRaft 集成和自定义日志存储；
- 内存状态机与统一 command handler；
- `Mocha` 逻辑时钟、时间轮和确定性过期；
- Start/Tail/End 并发快照及增量 CAS；
- 多 Key 命令分类和快照恢复；
- Redis RESP 命令模块与 Sentinel 风格发现。

参考 cache-cat 的模块职责、测试思路和不变量，不直接复制其 wire format、存储格式、配置默认值或特定时钟假设。

## 6. 成功标准

项目达到可写入简历的标准，需要至少证明：

1. 三节点集群可以完成 Leader 选举和写入复制。
2. 非 Leader 节点能明确拒绝或转发请求。
3. Leader 崩溃后集群能重新选举。
4. 已提交日志在节点重启后可以恢复。
5. Follower 落后时可以通过日志或快照追赶。
6. TTL 在不同节点重放后保持一致。
7. 网络分区不会产生两个都能安全提交写入的 Leader。
8. 协议错误、磁盘错误和非法输入不会导致进程崩溃。

## 7. 简历表达

建议最终使用类似表述：

> 使用 Rust 和 Raft 实现 Redis RESP2/RESP3 兼容的强一致分布式内存 KV 存储，支持 WAL、快照恢复、TTL、Leader 故障切换和多节点故障注入测试。

只有当对应测试真实存在时，才使用“强一致”“故障恢复”或“已提交数据不丢失”等表述。
