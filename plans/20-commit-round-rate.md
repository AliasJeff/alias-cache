# 20 leader 提交轮速率（写侧最后一层）

## 现状（2026-10-19，plans/19 + plans/18 Phase 2-4 落地后）

| 负载 | 当前 | cache-cat 同机 | 比例 |
| --- | ---: | ---: | ---: |
| 95/5（wp5） | 270.6k | 203-236k | **超越** |
| 纯写 | 95.5-104.3k | 185k | ~55% |
| 50/50 | 54.0-58.9k | 102-153k | ~50% |
| 5/95（wp95） | 104.8-115.6k | 152,440 | ~71% |

µs 级每条成本已全部出清（SM apply 0.545µs、RESP 编码直写、批量 size
公式化、去重缓存 O(1)）。剩余瓶颈锁定在**提交轮**：8192 在途（512 连接
× p16 流式）下，闭环 RTT ≈ 84ms → 吞吐 = 8192/84ms ≈ 98k，且对
coalescer 窗口参数不敏感（见下）。

## 已证伪的假设（A/B 实测，勿重试）

### 假设 1：20ms 组窗是每批的纯等待（证伪）

`RAFT_COMMIT_MAX_LATENCY` 20ms → 5ms，重建重测：

| 负载 | 20ms 窗 | 5ms 窗 |
| --- | ---: | ---: |
| 纯写 | 95.5-98.7k | 92.8-99.0k（不变） |
| 5/95 | 104.8-115.6k | **88.9k（-18%）** |

结论：吞吐对窗口不敏感（闭环自调节：窗口减半 → 每组条数减半、组频
加倍），而更小的组放大每组固定开销（prepare 锁段、openraft 往返、
apply 批次开销），混合档明显受损。**20ms 保持**。

### 假设 2：1024 条 chunk 上限造成并发拆分（负收益）

`CLIENT_BATCH_MAX_ITEMS` 1024 → 4096（每组单 chunk 单 append）：

| 负载 | 1024 cap | 4096 cap |
| --- | ---: | ---: |
| 纯写 | 95.5-98.7k | 102.6-104.3k（+5%） |
| 5/95 | 104.8-115.6k | 89.1-95.2k（-13%，且一轮 0.04% 错误） |

结论：单 chunk 利纯写、损混合——并发 chunk 为 openraft core 提供了
并行度，对混合负载价值大于单 append 的合并收益。**1024 保持**。

## 闭环算术（为何一维参数动不了它）

512 连接 × 流式 p16 = 8192 固定在途。吞吐 = 在途 / 平均 RTT。
RTT ≈ 组队等待 + prepare + openraft（append→复制→提交→apply）+
应答写。窗口 A/B 证明"组队等待"不是 RTT 主项——RTT 被下游某个对
组大小不敏感的串行段主导。尚无数据区分：

- (a) openraft core 单任务串行（client_write_many 处理、复制分派、tick）
- (b) apply 通知/响应 oneshot 唤醒路径（每轮 ~512 连接唤醒）
- (c) prepare 的 SM 写锁段与读 prepare 的争用
- (d) tokio 调度饱和（512 连接 + 3 节点同机 10 核）

## 下一步（本 plan 的实施步骤）

1. **轮相位仪表**：coalescer 轮加 4 段累计计时（queue-wait / prepare /
   raft-commit / respond），经 LogStoreMetrics 同款原子计数器暴露到
   INFO stats；一轮基准即可读出 10ms 去向。
2. 按 (a)-(d) 中命中者立项修复：
   - (a) 命中 → openraft 复制内环（是否可 upstream 配置/本地 patch）
   - (b) 命中 → 响应扇出合批（每轮一次批量唤醒）
   - (c) 命中 → prepare 分片或双缓冲
   - (d) 命中 → 基准分机部署（客户端独立一台），同机数字另列
3. 完成标准：5/95 ≥ 150k、50/50 ≥ 100k（同机同负载）；期间任何
   参数回调必须带三方 A/B 数据。

## 实验结果（2026-10-19，仪表已落地并合入）

相位仪表（`CommitRoundMetrics` → `INFO stats` 的 `commit_*` 字段 +
`raft_apply_lag`）落地后实测（3 节点新鲜集群、512c×p16、纯写 30s、
零错误；负载中 t=12s/24s 两次采样）：

| 层 | 测量 | 判定 |
| --- | --- | --- |
| coalescer 排队+组窗 | **12.9-20.4ms/条**（负载/累计口径） | 最大单项，但为下游反压的症状 |
| prepare | 5µs/条（累计）、22µs/条（负载中，含读锁争用） | 无辜（≤0.02ms） |
| admission | ~0µs/条 | 无辜 |
| openraft chunk 提交 | 累计 7.95ms/轮；**负载中 30ms+/chunk（max 685ms）** | 真正的串行段 |
| 应答扇出 | 0.2-1.2ms/轮 | 无辜 |
| `raft_apply_lag`（3 节点） | 负载中 **4032 → 8193 增长**；空载归零 | 未提交积压（等 follower），非 apply |
| `raft_apply_lag`（单节点对照） | **0-1，全程无积压** | SM/apply 无辜的确定性证据 |

**决定性对照（E5）：单节点纯写 = 150,042 ops/s（零错误），三节点
= 95.9-98.9k。** 单节点每条 raft 相位成本 ~8.5µs——本地路径（RESP +
coalescer + openraft 单机提交 + apply + 应答）能撑 150k+。

### 结论：瓶颈 = leader→follower 提交往返容量

三节点下每 chunk（~1000 条）的 append→复制→quorum 确认往返在负载中
耗 30ms+ 且在 openraft 内串行排队，管道只允许 ~98k 条/s 流入；上游
coalescer 的 20.4ms 排队是这一容量的反压表现（5ms 窗口 A/B 已证明
提前放行只会在 core 内堆队列，吞吐不变、混合档更差）。

排除清单（均有数据）：fsync/存储（plans/19 已修，0.31ms 平坦）、
SM apply（单节点 lag=0 + 0.545µs）、prepare、admission、响应扇出、
组窗参数（两轮 A/B 证伪）。

### 空载延迟地板（独立小发现）

1 连接 × p1 空载 SET p50 = **22.3ms** = 20ms 组窗 + ~2ms 真实路径。
组窗在空载时总是等满（`timeout_at` 到期才提交），这是纯延迟选择而
非吞吐需要。若要低空载延迟，可做"仅当上一组仍在提交时才等窗"的
自适应窗口——不影响吞吐上限（负载中窗口不 binding 已证）。

### 下一层归因对象（本 plan 的第 2 步）

openraft 复制内环：为什么每 chunk 往返在 loopback 上耗 30ms+。
候选机制：(i) leader 每 follower 的 AppendEntries 串行轮次 + ack
RTT 累积；(ii) openraft 复制流控窗口（`max_payload_entries` 之外
的内部限制）；(iii) follower 侧 receive→append→ack 路径的调度延迟。
工具：给 follower 接收路径加同款相位计数；对照 cache-cat 同配置
的复制参数；必要时读 openraft 0.10.0-alpha.34 复制源码逐段排除。
