| 负载 | 当前 | cache-cat 同机 | 比例 |
| --- | ---: | ---: | ---: |
| 95/5（wp5） | 270.6k | 203-236k | **超越** |
| 纯写 | 95.5-104.3k | 185k | ~55% |
| 50/50 | 54.0-58.9k | 102-153k | ~50% |
| 5/95（wp95） | 104.8-115.6k | 152,440 | ~71% |

µs 级每条成本已全部出清（SM apply 0.545µs、RESP 编码直写、批量 size
公式化、去重缓存 O(1)）。剩余瓶颈锁定在**提交轮**：8192 在途（512 连接

coalescer 窗口参数不敏感（见下）。

## 已证伪的假设（A/B 实测，勿重试）

### 假设 1：20ms 组窗是每批的纯等待（证伪）

`RAFT_COMMIT_MAX_LATENCY` 20ms → 5ms，重建重测：

| 负载 | 20ms 窗 | 5ms 窗 |
| --- | ---: | ---: |
| 纯写 | 95.5-98.7k | 92.8-99.0k（不变） |
| 5/95 | 104.8-115.6k | **88.9k（-18%）** |

结论：吞吐对窗口不敏感（闭环自调节：窗口减半 → 每组条数减半、组频
加倍），而更小的组放大每组固定开销（prepare 锁段、openraft 往返、
apply 批次开销），混合档明显受损。**20ms 保持**。

### 假设 2：1024 条 chunk 上限造成并发拆分（负收益）

`CLIENT_BATCH_MAX_ITEMS` 1024 → 4096（每组单 chunk 单 append）：

| 负载 | 1024 cap | 4096 cap |
| --- | ---: | ---: |
| 纯写 | 95.5-98.7k | 102.6-104.3k（+5%） |
| 5/95 | 104.8-115.6k | 89.1-95.2k（-13%，且一轮 0.04% 错误） |

结论：单 chunk 利纯写、损混合——并发 chunk 为 openraft core 提供了
并行度，对混合负载价值大于单 append 的合并收益。**1024 保持**。

## 闭环算术（为何一维参数动不了它）

512 连接 × 流式 p16 = 8192 固定在途。吞吐 = 在途 / 平均 RTT。
RTT ≈ 组队等待 + prepare + openraft（append→复制→提交→apply）+
应答写。窗口 A/B 证明"组队等待"不是 RTT 主项——RTT 被下游某个对
组大小不敏感的串行段主导。尚无数据区分：

- (a) openraft core 单任务串行（client_write_many 处理、复制分派、tick）
- (b) apply 通知/响应 oneshot 唤醒路径（每轮 ~512 连接唤醒）
- (c) prepare 的 SM 写锁段与读 prepare 的争用
- (d) tokio 调度饱和（512 连接 + 3 节点同机 10 核）

## 实验结果（2026-10-19，仪表已落地并合入）

### 第二轮实验（RPC 探针 + worker 对照 + 同日基线重测）

在相位仪表之上追加了复制 RPC 探针（`raft_append_rpc_*` / 
`follower_append_*` → INFO stats）并做了两个对照实验：

**E6（RPC 探针，512c×p16 纯写 30s，零错误）**：

| 指标 | 测量 | 判定 |
| --- | --- | --- |
| leader RPC 往返 | 均值 1.67ms / max 30ms / 278 RPC/s | 单次往返健康 |
| **over_soft_ttl（撞 37.5ms 超时）** | **0** | **超时抖动假设证伪** |
| follower 处理耗时 | 均值 554µs / max 20.8ms | follower core 无辜 |
| 每 follower 链路利用率 | ~23%（139 RPC/s × 1.67ms） | 复制链路远未饱和 |

**E7（worker 线程上限 3/节点，排除 CPU 超订阅）**：吞吐不升
（109-112k），且一轮出现 6% 错误风暴、5/95 降到 64-74k——线程不足
破坏稳定性。**CPU 超订阅假设证伪**（默认全核更优）。

**同日基线重测（安静机器，默认 worker，全部零错误）——机器噪声曾
严重污染基线**：

| 配置 | 纯写 | 与旧基线对比 |
| --- | ---: | --- |
| 3 节点 | **150.7-162.6k（中位 159k，三轮稳定）** | 旧基线 98-116k 被机器负载压低 ~35% |
| 单节点 | **208-237k（中位 223k）** | 旧基线 150k 同样偏低 |
| 95/5 | **380,484** | 历史新高（cache-cat 同机 203-236k 的 1.6-1.9×） |
| 5/95 | 104,916 | cache-cat 152k 的 69% |
| 50/50 | 59,868 | cache-cat 102-153k 的 39-59% |

**修订结论**：

1. **复制的真实税负 ≈ 29%**（同日 223k → 159k），远小于早前
   "98k vs 150k"暗示的 53%——那组对比混合了机器噪声。
2. 单节点 223k 已**超过 cache-cat 同机 185k**——本地路径（RESP +
   coalescer + openraft 单机 + SM + 应答）不再是差距来源。
3. 复制内各组件（RPC 往返、follower 处理、链路利用率）全部低负载
   且无超时。3 节点 160k = cache-cat 纯写 185k 的 86%。
4. **测量纪律（新增）**：同一二进制的吞吐可因机器背景负载波动
   ±35%；任何 A/B 结论必须以同机同时窗的对照为准，跨时段基线
   只能证方向、不能定量。

### 剩余差距的结构（安静机器口径）

纯写已到 cache-cat 的 86%；混合档（50/50 40-59%、5/95 69%）仍受
闭环 RTT 结构压制：8192 在途 ÷ RTT（~50-70ms，其中组队等待占
大头）= 吞吐。下一步可动、且不会被机器噪声掩盖的杠杆：

- (i) **管线化 `stream_append`**：TcpNetwork 实现真正的流式复制
  （持久连接 + 有界在途请求），消除每 RPC 连接建立
  （`send_rpc` 每次 connect+close）并让 follower 存储同步跨 RPC
  合流；预期缩短 ~29% 复制税的一部分。
- (ii) **自适应组窗**（仅延迟收益）：空载 SET p50 22.3ms = 20ms
  窗等满；"仅当上一组仍在提交时才等窗"可把空载/轻载延迟降到
  ~2-5ms，不影响吞吐上限（已证窗口不 binding）。
- (iii) **分机基准**：客户端与集群分机部署，量出共享机器剩余的
  本底争用，为 50/50 的归因画上句号。
